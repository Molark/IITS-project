# Каталог E2E-сценариев

Шаги выполняем через API АРМ, результат проверяем в данных: БД, Kafka, эмуляторы, аудит. Все записи одного прогона связаны `correlation_id`.
Данные — в [test-data.md](./test-data.md).

| ID | Сценарий | Негативные ветки | Требования |
|---|---|---|---|
| E2E-01 | Выдача с оплатой при получении | Отказ банка, банк молчит, повтор команды, подмена суммы | FR-01, FR-02, FR-05, NFR-04, T-02 |
| E2E-02 | Выдача предоплаченного заказа без связи | НП без связи, обрыв при синхронизации, маркетплейс недоступен | FR-03, FR-04, NFR-02, NFR-03, T-08 |
| E2E-03 | Закрытие смены и выгрузка в ERP | ERP недоступна, дубль события, закрывает оператор | FR-06, DQ-03 |
| E2E-04 | Возврат выдачи старшим смены | Возврат делает оператор, нет причины, банк не ответил | T-03, T-04 |

## E2E-01. Выдача с оплатой при получении

Данные: TD-01. Эмулятор банка отвечает «оплачено».

Шаги: найти заказ по коду → проверить получателя → запустить оплату → зафиксировать выдачу.

Проверки:
* БД выдачи: одна выдача со статусом «выдан» и `payment_id`;
* эмулятор банка: одно списание на 249000 копеек;
* Kafka: одно `PaymentStatusChanged` (`paid`) и одно `OrderIssued`;
* эмулятор маркетплейса: статус «получен» один раз;
* аудит: выдача и оплата записаны.

| Ветка | Что делаем | Ожидаем |
|---|---|---|
| Отказ банка | Банк отвечает кодом `51` | `declined`, кнопка «Выдать» заблокирована, выдачи нет |
| Банк молчит | Банк не отвечает, часы +61 с, потом приходит «оплачено» | Сначала `unknown` и «Платёж не определён», новая оплата → 409. После ответа `paid`, списание одно |
| Повтор команды | `POST /v1/issues` дважды с одним `issue_id` | Второй ответ 200, в БД одна выдача |
| Подмена суммы | В запросе сумма 1 ₽ и статус «оплачено» | Поля игнорируются, списано 2 490 ₽ |

## E2E-02. Выдача предоплаченного заказа без связи

Данные: TD-02.

Шаги: выключить связь → выдать 30 предоплаченных заказов → часы +4 ч → включить связь.

Проверки:
* очередь АРМ: после синхронизации пустая;
* БД выдачи: ровно 30 выдач, `occurred_at` — время на точке;
* Kafka: 30 `OrderIssued` с `issued_offline = true`;
* эмулятор маркетплейса: 30 статусов, каждый один раз.

| Ветка | Что делаем | Ожидаем |
|---|---|---|
| НП без связи | Открыть заказ с НП | Кнопка «Выдать» заблокирована |
| Обрыв при синхронизации | Связь пропадает после 12 событий | Остальные уходят позже с теми же ID, итог 30 выдач |
| Маркетплейс недоступен | Эмулятор отвечает 5xx 30 минут | Шлюз повторяет отправку, в итоге дошли все 30 |

## E2E-03. Закрытие смены и выгрузка в ERP

Данные: TD-03.

Шаги: старший смены закрывает смену → сверка формирует реестр → адаптер ERP отправляет пакет.

Проверки:
* сверка: 35 выдач, сумма НП равна сумме оплат `paid`;
* расхождения: ровно одно — заказ без подтверждения выдачи;
* хранилище: те же 35 выдач и сумма;
* эмулятор ERP: один документ на `shift_id`.

| Ветка | Что делаем | Ожидаем |
|---|---|---|
| ERP недоступна | Эмулятор ERP выключен | Смена закрыта, пакет в очереди, отправится позже |
| Дубль события | Одно `OrderIssued` приходит в сверку дважды | Выдача учтена один раз |
| Закрывает оператор | Оператор вызывает закрытие смены | 403, запись в аудите |

## E2E-04. Возврат выдачи старшим смены

Данные: TD-04.

Шаги: старший смены оформляет возврат с причиной → адаптер оплаты возвращает платёж.

Проверки:
* БД выдачи: старая выдача не изменилась, добавлен возврат с причиной;
* эмулятор банка: один возврат;
* Kafka: `PaymentStatusChanged` (`refunded`);
* аудит: кто, когда и почему оформил возврат.

| Ветка | Что делаем | Ожидаем |
|---|---|---|
| Возврат делает оператор | Оператор вызывает возврат через API | 403, запись в аудите |
| Нет причины | Возврат без причины | 422 |
| Банк не ответил | Эмулятор молчит | `refund_pending`, повтор с тем же ключом, возврат один |
